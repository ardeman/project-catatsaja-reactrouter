# AGENTS.md

Instructions for AI coding agents working in this repo. Read `README.md` for the overview, setup, commands and layout. This file does not repeat them.

## Definition of done

A change is done only when the **Checks** command in `README.md` passes. If you can't run it, say so; don't claim it passed. The Firestore rules have tests (`pnpm test:rules`) and encryption and sharing have end-to-end tests (`pnpm test:e2e`), both run before every deploy; extend `tests/e2e/` when you change how items are stored, shared or unlocked. Other UI has no tests yet, so for UI changes also look at the result in `pnpm dev`, in both light and dark mode and both languages.

## Conventions

- Keep independent end-to-end scenarios out of the dependent Ana/Budi/Cici sequence in `tests/e2e/encryption.test.mjs`. Each independent scenario creates its own accounts. A new suite must be listed in both the workflow's `e2e` matrix and `pnpm test:e2e`. Update the suite descriptions in `README.md`, which owns the commands and execution layout.
- Use Conventional Commit subjects; see `README.md` for the format and hooks.
- Fix ESLint and knip findings; don't silence them with `eslint-disable` or knip ignores unless you add a comment saying why.
- Import app code through the `~/` alias (`~/lib/...`, `~/components/...`), not relative paths that climb out of a folder.
- Files and folders use `kebab-case`. Components are arrow functions with named exports; only route modules use a default export.
- Route modules in `app/routes/` stay thin: they render one component from `app/components/pages/<page>/` and hold no logic.
- A page folder has `index.tsx` (the exported page), and as needed a `context.tsx` for page state, a `type.ts` for its prop types, and one file per part. Files that touch browser-only APIs end in `.client.tsx`.
- Firestore calls live only in `app/apis/firestore/<collection>.ts`. Components reach data through one hook per action in `app/lib/hooks/` (`use-get-*`, `use-create-*`, `use-update-*`, `use-delete-*`); never call Firestore from a component.
- Gemini calls live only in `app/apis/ai/<feature>.ts`, through Firebase AI Logic (never an API key in the app), importing `firebase/ai` on demand so it stays out of the main bundle; the model is `geminiModel` in `app/lib/constants/ai.ts`. An AI feature sends data only when the person acts (choosing a photo, pressing a button), through `useAiConsent` and `AiNotice` (the one-time notice; `aiConsent` on the profile, taken back in Settings → Account), shows the result to check before anything is added or changed, and is described in the privacy policy. Check a model's answer with a Zod schema before using it, and add the feature's prompt and a fixed answer to `tests/e2e/ai.test.mjs`.
- Types go in `app/lib/types/<domain>.ts` with a `T` prefix (`TNoteResponse`, `TCreateNoteRequest`); Zod schemas go in `app/lib/validations/<domain>.ts`.
- Zod 4 style: pass messages as `{ error: t(...) }` (not `message`), and use top-level formats such as `z.email()`. A schema that coerces (`z.coerce`) has a different input type, so its form uses `useForm<z.input<...>, unknown, z.output<...>>`.
- Notes, tasks, finances and health logs are shared through `permissions.read` and `permissions.write` lists of user ids; `owner` is the creator. Keep queries, writes and `firestore.rules` consistent with each other: an update must match one of the cases in `canUpdateShared` (owner, a writer changing the content fields, anyone pinning or archiving for themselves, a reader leaving, someone invited accepting or declining). Sharing invites: the person goes in `invites.read` / `invites.write` and joins `permissions` only by accepting; the owner can't add anyone to `permissions` directly, and a new item starts with only its creator. The app invites one person per update, appended to `invites.read`, so the rules can refuse someone who blocked the owner (`users/{uid}/blocked/{id}`, private to its owner). A new content field goes in that collection's list in the rules and in `contentFields` (`app/lib/utils/encrypted-document.ts`), so it is encrypted too.
- Shared items are read and written through `app/apis/firestore/shared-document.ts` (create, update, share, leave, subscribe), which handles end-to-end encrypted items and plain ones alike; a collection module only adds what is specific to it (pinning, deleting). Never write an item's content fields directly, or an encrypted item would get readable text.
- Only content edits set `updatedAt`. Pinning, archiving, sharing and leaving must not, or they change the "edited" date and the list order.
- A list page renders `Collection` (`app/components/base/collection`): loading and empty states, pinned and other sections, the person's archived items folded away at the bottom (`archivedBy`, per person like `pinnedBy`), newest first, and filtering by `?q=` (set by "See all" in the navbar's global search, `layouts/navbar/search.tsx`). Cards open through a link that covers the card (see `notes/card.tsx`), and masonry cards are `w-full sm:w-80`.
- A detail form saves with `useAutosave` and a `save()` that writes only what differs from the stored document, so it can run any time (idle, leaving, the Save button). It takes the stored item through `useStoredValues` (`defaultValues` plus the hook, never `values` with `keepDirtyValues`, which kept a stale copy and wrote deleted entries back), with `mergeById` for lists whose items have an `id`. New items are created when leaving with content, never discarded behind a prompt. Show `SaveStatus` next to the date, and lock every input for read-only users.
- Show Firebase errors with `getErrorMessage` (`app/lib/utils/firebase-error.ts`), never `String(error)`; add new codes to its map and to `errors.*` in both languages.
- Icon-only buttons need an `aria-label` and a `title` from the translations. Toasts can't be reached while a modal dialog is open, so an undo inside a dialog goes in the dialog.
- `app/components/ui/` holds generated shadcn/ui primitives: add them with the shadcn CLI and don't restyle them in place. App-specific variants go in `app/components/base/`.
- Style with Tailwind classes and `cn()` (`~/lib/utils/shadcn`); colors come from the CSS variables in `app/styles/`, so both themes work.
- Tailwind 4 is configured in CSS only: theme, plugins and the `dark` variant live in `app/styles/tailwind.css`. Don't add a `tailwind.config.*` or `postcss.config.*`. Other CSS files that use theme values start with `@reference './tailwind.css'` and use `--theme(...)`.
- Tailwind 4's `space-y-*` adds a bottom margin, which does nothing on an inline element such as a `<label>`. For a stack that starts with a label, use `[&>:not([hidden])~:not([hidden])]:mt-*` (the v3 rule, as in `app/components/base/input/`); elsewhere prefer `flex`/`grid` with `gap-*`.
- User-facing text goes in both `app/localization/locales/en/` and `id/` (`common.json`, validation messages in `zod.json`); never hardcode strings.
- When a change people can notice is released, add it to `app/content/changelog.ts` in both languages: plain words about what changed for them, tagged new, improved or fixed. Group changes released together under one date.
- Read environment variables only through `app/lib/utils/environment.ts`.
- Public pages (`publicPages` in `app/lib/configs/page.ts`, and `prerender` in `react-router.config.ts`) are rendered at build time in English and must not wait for Firebase Auth or touch browser APIs (`window`, `localStorage`, `document`) while rendering; do that in effects. A new public page goes in both lists and in `PUBLIC_PAGES` in `public/sw.js`.
- `public/sw.js` must never serve an outdated app while online: pages stay network-first, and it leaves cross-origin requests (Firebase, Firestore) alone. When you change what it caches or how, bump the cache names (`pages-v2`, `assets-v1`) so old caches are dropped.
- Theme: `ThemeHead` (`app/components/layouts/theme-head`) runs before the first paint on every page, including the start-up fallback: it applies the saved theme and size and creates the single `theme-color` tag, the `apple-mobile-web-app-status-bar-style` tag (iOS ignores `theme-color` in the installed app) and the tab's icon (`favicons`, the logo that stands out on the theme), which `ThemeProvider` keeps in step with the app's theme. Don't render any of them from React or route `meta`/`links`: React would add a second copy. Show the logo with `Logo` (`app/components/base/logo`), which follows the theme the same way.
- The installed app never shows the landing page: the inline script in `app/components/layouts/theme-head` leaves `/` before the first paint, and `middleware` redirects in-app visits to it (`isStandalone`). It opens on the person's start page instead (also the first page of a session at the manifest's `/notes`, and after signing in), except that a relaunch within an hour of going to the background returns to the last page (`last-visit` in `localStorage`, kept by `useRememberLastVisit`), since a phone may unload a backgrounded app. The start page and menu order are saved on the profile (`navOrder`, `startPage`); the start page is also kept in `localStorage` (`app/lib/constants/navigation.ts`) because the script runs before the profile loads.
- Installing: the manifest comes from `scripts/generate-manifest.mjs` (run by `pnpm build`); app-wide meta tags come from `withAppMeta` (`app/lib/constants/metadata.ts`), which a route with its own `meta` must use.

## Guardrails

- **Dependencies:** add packages with `pnpm add` (not by editing versions by hand) and commit `pnpm-lock.yaml`. knip fails on unused dependencies, so remove what you stop using. Never relax pnpm's `minimumReleaseAge` or approve a package in `allowBuilds` (`pnpm-workspace.yaml`) without the user's approval; when a package asks to run an install script, say what the script does.
- **Firestore rules:** any new collection, field used for access or query needs matching rules in `firestore.rules` (and an index in `firestore.indexes.json` if the query needs one). Never loosen a rule to make a feature work. Change `tests/firestore-rules.test.mjs` with the rules: a new collection gets its own cases, and what must be refused is tested as well as what is allowed.
- **Deployment:** pushing to `main` deploys to production. Before a deploy that could break the running app (changing stored data, or rules that refuse what the deployed app writes), suggest turning on maintenance mode first (README → Deployment → Maintenance mode), and turning it off after checking. A change to how data is stored also raises `appVersion` (`app/lib/constants/app-version.ts`) so tabs left open on the old app are asked to reload (`minAppVersion`, same section). Commit and push only when asked. Deploying Firestore or the Cloud Functions (`firebase deploy`) or setting repository secrets needs the user's explicit approval.
- **Secrets:** never commit `.env`, API keys or service account files. A new variable goes in `.env.example`, `environment.ts`, the workflow's build `env` and the README's environment table.
- **Generated files:** don't edit `public/site.webmanifest` (change `app/lib/constants/metadata.ts`), the icons in `public/` (change `scripts/icon/logo.svg` and run `pnpm generate:icons`), `.react-router/` or `build/`.

## Decisions

Record architectural choices here as one line each: date, decision, reason.

- 2026-10-15: Group shared icons, UI libraries and public UI components in the production bundle to reduce small script requests; keep feature modules dynamically split so public pages do not load the editor, AI or private data APIs early. README → Google Search Console owns the build details.

- 2026-10-18: Notifications (the bell, `app/components/layouts/notifications`) are worked out on the device from what the app already has (invitations, due reminders, the once-a-day count of encrypted items others can't read, and `/version.json`, written by `vite.config.ts`, for a newer deploy), never stored: an item leaves the list once it's dealt with, so there is nothing to mark read and nothing new for the rules or end-to-end encryption. The one exception is "What's new" (releases in `app/content/changelog.ts` after the profile's `seenRelease`, or after the account was made), saved on the profile so it clears on every device; `/changelog` is public and loads no Firestore, so only the bell marks it seen.
- 2026-10-09: Single-page app (`ssr: false`) on Firebase Hosting, with every path rewritten to `index.html`, so no server is needed.
- 2026-10-09: Firestore data is read with live `onSnapshot` listeners inside hooks, not a query cache library, so shared notes and tasks update in real time.
- 2026-10-09: Node 24 LTS and pnpm 12 (through Corepack). React Router 8 and lint-staged 17 need Node 22.22 or later; pnpm 12 refuses releases younger than a day and runs no dependency install scripts unless allowed. The three that ask (`@firebase/util`, `protobufjs`, `unrs-resolver`) are denied: none is needed for this app.
- 2026-10-09: `remix-i18next` removed. Version 8 only offers a server middleware, and this app renders on the server only at build time, so `app/localization/i18next.server.ts` reads the language cookie and the routes' `handle.i18n` itself.
- 2026-10-09: Tailwind 4 with `@tailwindcss/vite` and a CSS-only config, `tw-animate-css` instead of `tailwindcss-animate`, and Vite's own `resolve.tsconfigPaths` instead of `vite-tsconfig-paths`. Checked against production: public pages match pixel for pixel in both themes, apart from icons lucide redrew.
- 2026-10-09: ESLint 10, because every ESLint 9 release is deprecated. `eslint-plugin-react`, `-import` and `-jsx-a11y` don't support it yet and run through `@eslint/compat`; the rules newer unicorn and react-hooks versions added are on, except `react-hooks/incompatible-library` (README → Roadmap).
- 2026-10-09: TypeScript stays on 6.0: typescript-eslint supports only versions below 6.1.
- 2026-10-09: Firestore rules check each kind of update on shared documents separately. Before, anyone with read access could write, so read-only sharing was not enforced.
- 2026-10-09: The share dialog loads only the profiles of the people an item is shared with (by id, 30 per query). It used to read the whole `users` collection.
- 2026-10-09: Sign-up writes the profile before sending the verification email, and signing in recreates a missing profile: a failed email had left accounts without one, unable to create anything or be found for sharing.
- 2026-10-09: The landing page and the other public pages are prerendered (React Router `prerender` with `ssr: false`) so search engines and link previews can read them; everything else stays client-only via `__spa-fallback.html`. They hydrate in the build language and then switch to the saved one (`app/entry.client.tsx`), so the text matches during hydration; an inline script applies the saved theme before the first paint.
- 2026-10-09: Hosting sends pages with `Cache-Control: no-cache` and `/assets/` as immutable for a year. With Firebase's default one-hour caching, a deploy left browsers with cached pages pointing at deleted asset files.
- 2026-10-09: Installable as a standalone app: a full manifest (start at `/notes`, maskable icons, shortcuts), Install buttons from `useInstallApp` (the browser prompt, or that browser's own steps; hidden where installing is impossible, such as Firefox on desktop), and a small hand-written service worker for offline start. No PWA library: the app needs only a shell cache, and a hand-written worker keeps the caching rules visible.
- 2026-10-10: Finances are books of entries. A book has its own currency; each entry stores its own currency and the rate into the book's currency (prefilled from the person's currency settings, where a rate is the value of 1 unit in their default currency), so totals are fixed and the same for everyone a book is shared with. Totals are computed (quantity × amount × rate), never stored.
- 2026-10-10: Category suggestions come from the person's own entries, computed in the browser: nothing leaves the device. They never override a category or type the person chose. AI (Gemini via Firebase AI Logic) was considered and left for later.
- 2026-10-11: Category suggestions use an on-device naive Bayes classifier (`app/lib/utils/category-classifier.ts`) trained on the person's entries plus a bilingual starter word list (`app/lib/constants/category-keywords.ts`), not a cloud AI: free, offline, and compatible with end-to-end encryption. Only a guess of 90% or more may switch income and expense. `pnpm test:unit` checks its accuracy on typical descriptions.
- 2026-10-10: Collection API modules own live Firestore subscriptions; the action hooks use `useLiveData` for auth, loading and cleanup, so a page closed while auth is loading cannot start a listener after unmounting.
- 2026-10-10: A book's accounts (wallets, bank accounts and what they hold, in the book's currency) are stored on the book, so everyone it is shared with checks against the same numbers. The difference from the book's balance is computed, never stored.
- 2026-10-11: Finance charts are hand-drawn SVG (`app/components/pages/finance-detail/*-chart.tsx`), not a chart library: the app needs two simple charts, and SVG keeps the marks, tooltips and both themes under our control. Analysis is computed in the browser from a book's entries (`app/lib/utils/finance-analysis.ts`), never stored.
- 2026-10-11: Finance categories share seven validated colours by group (`--cat-1` … `--cat-7`, plus neutral for "other"), not a colour each: past about eight, colours can't be told apart, especially with colour blindness. A category's colour always appears with its icon and name.
- 2026-10-11: Health logs (`healthLogs`) are one per person, shared like books, with measurements in a `content` array (lab values stored in mg/dL, converted for display). Reference ranges and their sources live in `app/lib/constants/health.ts`; results are shown as ranges, never as a diagnosis.
- 2026-10-11: Child growth uses the WHO Child Growth Standards from WHO's own expanded tables (`app/lib/constants/who-growth-standards.ts`, generated: don't edit by hand), kept daily to 13 weeks and around day 731 and weekly otherwise (within 0.0022 z of the daily tables), loaded only when a child's growth is shown.
- 2026-10-11: Profiles (`users`) can be read one at a time but not listed: a list query let any signed-in user download every email and name. Finding someone by email goes through `userLookup/{email}` (their id only; each person files only their own sign-in email, synced on load by `fetchUserData`).
- 2026-10-11: End-to-end encryption on Web Crypto only: an RSA-OAEP key pair per person (private key sealed with their passphrase via PBKDF2, their recovery code, or a passkey via the WebAuthn PRF extension, in owner-only `users/{uid}/keys/main`), and per item an AES-GCM content key sealed for each person with access (`keys`), with the content fields as one `encrypted` blob. Owner, permissions, pins and dates stay readable for the rules and lists. Opt-in for existing accounts, offered at sign-up for new ones (`encryptionRequired`, which they can decline); plain and encrypted items work side by side, an encrypted item shared with someone without keys is stored plain only if the owner agrees, and removing someone gives the item a new key. Turning it off stores the person's own items plain again and deletes their keys; items others encrypted for them become unreadable to them until the owner, told in Settings → Account, chooses to share them unencrypted (never automatically). Trade-off: an encrypted item is one blob, so two people editing it at the same moment can overwrite each other.
- 2026-10-11: Gemini through Firebase AI Logic on the Gemini Developer API's no-cost tier, with App Check enforced for it, instead of a Gemini API key built into the app (anyone could have copied it). The first feature is receipt scanning: Gemini only reads the receipt; dates, currencies, discounts and categories are worked out in the app (`app/lib/utils/receipt.ts`, tested by `pnpm test:unit`), so the person's own category history still decides. Trade-off: on the no-cost tier Google may use the photos to improve its services, which the notice and the privacy policy say; photos leave the device even for encrypted books, but only when chosen.
- 2026-10-12: Child growth from 5 to 19 years uses the WHO Growth Reference 2007 from WHO's own z-score tables (`app/lib/constants/who-growth-reference.ts`, generated: don't edit by hand), every month as published, interpolated by age and loaded only when a child of that age is shown; it takes over from the standards after day 1,856. WHO publishes weight-for-age only to 10 years, so past 10 the app points to BMI-for-age. Status from 5 follows PMK No. 2/2020 for BMI-for-age (5–18 years) and WHO's cut-offs for height-for-age. The maths (`app/lib/utils/growth.ts`) has no app imports and is tested against WHO's published values by `pnpm test:unit`.
- 2026-10-12: Health reminders live in the log's encrypted content (`reminders`) and are worked out in the browser (`app/lib/utils/health-reminders.ts`): due ones show in the app, and a calendar file (.ics) lets the phone alert on time. Push notifications were left out: they need Cloud Functions (the Blaze plan) and a server that can read reminder times, which end-to-end encryption rules out.
- 2026-10-12: The app earns from an optional Plus subscription (README → Roadmap → Revenue), never from ads, trackers that see content, or selling data: end-to-end encryption and "not even we can read it" are what it sells. The core stays free (the About page promises it) and nothing people already have moves behind the paywall. A plan is written only by a server (a Cloud Function on the payment notice), never by the app, and Firestore rules keep users from changing it.
- 2026-10-12: The workflow takes nothing from the runner image (Node from `.nvmrc`, pnpm from `packageManager`, Java from setup-java, Chrome from Playwright, a pinned Firebase CLI), checks pull requests and runs weekly without deploying, and Dependabot updates the actions: so `ubuntu-latest` moving to a new Ubuntu (26.04 from 2026-10-19) or an action's runtime going away shows up in a check, not a failed deploy.
- 2026-10-13: New accounts may decline end-to-end encryption on the setup screen (`encryptionRequired` set to false) and turn it on later in Settings, like older accounts, so encryption (with the passphrase and recovery code it asks for) is a choice, not a condition for using the app.
- 2026-10-13: Sharing is an invitation the other person accepts or declines (`invites` on the item, enforced by the rules), so nothing appears in someone's lists without their consent. Items shared before stay shared. An invited person's key is sealed when they are invited, so the invitation can show the title; that means they can read the item before answering, and cancelling an invitation re-keys it like removing someone.
- 2026-10-13: Maintenance mode is a `config/app` document set in the Firebase console, read live by the app (and readable signed out, so the sign-in pages show it too): it closes the app at once without a deploy or reload, and needs no admin screen or server.
- 2026-10-13: Firestore uses its persistent offline cache (IndexedDB, shared by tabs), so saves made offline survive a reload and upload later; signing out waits a moment for them, then deletes the cache and reloads. Unsaved new entries and Quick add text are kept as drafts (`app/lib/utils/drafts.ts`), never uploaded; an encrypted book's draft lives in `sessionStorage` only, so its readable text doesn't outlive the tab.
- 2026-10-13: Blocking is a private list per person (`users/{uid}/blocked`), checked by the rules when someone is invited, so it holds even against a modified app; the blocked person only hears that the invitation couldn't be sent, never why.
- 2026-10-13: Firestore (`app/lib/configs/firestore.ts`) and App Check (`app-check.ts`, which Firestore and AI Logic take the app from) start apart from sign-in and Analytics (`firebase.ts`), so the public pages, which only check who is signed in, load neither them nor reCAPTCHA. Analytics stays on them for the promo links' campaigns. App Check is enforced for AI Logic and, since 2026-10-26 (after a week at 100% verified), Cloud Firestore; enforcing it for Authentication would need it back in `firebase.ts`. With `"sideEffects": false`, a module whose import starts something must export a value it produces, not re-export, or the bundler skips it.
- 2026-10-13: A book's entries are stored one document per month (`finances/{id}/months`, `app/lib/utils/finance-months.ts`), not in the book: a document is capped at 1 MiB (a few thousand entries), and per-entry documents would cost a read per entry on each new device and make re-keying rewrite every entry. Encrypted months are one blob each, with ids derived from the book's key (HKDF, then HMAC) so the server sees only how many months there are; a key or mode change rewrites every month in the same batch as the book, which the rules check against the book after the write. The book keeps a `summary` (totals, spending, 50 newest entries) for lists, search and suggestions. Every book has `entryStore` 2 and no `content` (books from before moved when first opened; once all had, on 2026-10-14, the move code went), which the rules require. No paging of entries: totals, charts and suggestions need them all, and the offline cache downloads only changed months.
- 2026-10-18: Push notifications (invitations, health reminders, every medicine dose) through Firebase Cloud Messaging and Cloud Functions on the Blaze plan, superseding the 2026-10-12 choice to leave them out. Their text is sealed on the writing device for each receiving device (ECDH P-256 key per device, private half in IndexedDB for `public/sw.js`), so the server stores only send times, recipients and ciphertext, with a generic text as fallback. Trade-off, stated in the privacy policy: the server learns when reminders are due. The app writes `pushMessages` (invitations) and `healthLogs/{id}/pushSchedule` (reminders), checked by the rules; the hand-written service worker shows them, with no `firebase-messaging-sw.js`.
- 2026-10-18: The Cloud Functions are deployed by hand (`deploy --only functions`), like the rules, so the workflow's service account keeps only its Hosting roles. Cloud Build installs them with npm, so `functions/package-lock.json` is generated by `pnpm lock:functions` (npm's `--before`, one day back, matching pnpm's minimum release age) and checked by `pnpm validate` and the predeploy.
- 2026-10-26: The calendar file (.ics) for health reminders and medicines is gone: push notifications alert on time, so one way to be alerted is kept. Trade-off: no on-time alert where push can't reach (an iPhone without the installed app, Firefox on desktop, notifications refused); those reminders still show in the app.
- 2026-10-18: End-to-end tests that only check the interface (`tests/e2e/ui.test.mjs`) don't block a deploy; the suites guarding stored, shared and encrypted data do. Every suite gets one retry on CI, and docs-only changes skip them: a flaky formatting test had held back a release. README → Commands owns the details.
- 2026-10-27: A book's own groups of categories (such as Needs = food + bills) are stored on the book, as a content field, not on the profile: everyone the book is shared with sees the same groups and totals, and they are encrypted with the book. Trade-off: they can't be reused across books; comparing books uses categories only.
- 2026-10-26: The fertile window reminder on a shared health log goes to the owner only unless they mark it `shared`, enforced by `ownerOnly` on `healthLogs/{id}/pushSchedule` in the rules: who else learns about someone's fertility is the owner's choice, not a side effect of sharing the log.
- 2026-10-27: Plus is `plan: 'plus'` and `planEndsAt` on the profile, which the rules refuse to let the person set or change (a server or the Firebase console writes them); the app checks it with `usePlan`. A book's groups of categories are the first Plus feature: anyone the book is shared with sees them, only a writer with Plus changes them, and each category is in one group at most so the shares add up to 100%. The lock is in the app only: the rules can't see groups inside an encrypted book, and checking them on plain books would refuse turning encryption off or copying a book once Plus ended. Groups cost nothing to run, so a modified app getting around it loses nothing.
- 2026-10-27: Budgets (a monthly limit per expense category, in the book's currency) are a Plus feature stored on the book as a content field, locked in the app like groups: everyone the book is shared with sees the same limits, encrypted with it. What is left is computed in the browser for the current calendar month, never stored.
- 2026-10-27: Savings goals (a name, an amount, a due month and, once done, what it cost) and the payday they are saved on are Plus content fields on the book (`goals`, `payday`), locked in the app like groups and budgets, so everyone the book is shared with sees the same plan. The plan is computed in the browser (`app/lib/utils/savings-goals.ts`): savings are the accounts' total when any balance is entered, otherwise the book's balance; a goal due in a month counts the paydays from today to the end of the month before, so the money is there when the month starts; done goals leave the plan.
- 2026-10-28: A book's keywords (words looked for in entries' descriptions, commas for alternatives) are a Plus content field on the book (`keywords`), locked in the app like groups, so everyone it is shared with sees the same totals. Matching is case-insensitive substring, computed in the browser (`app/lib/utils/keywords.ts`); an entry may count under several keywords, so their shares need not add up to 100%.
- 2026-10-27: A card's colour and background emoji (`cardStyle`) are one setting per item, chosen by the owner or a writer and seen by everyone it is shared with, stored as a content field so encrypted items keep them encrypted; unlike pins and archiving, they are not per person.
